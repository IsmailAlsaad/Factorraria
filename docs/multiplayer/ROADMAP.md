# Factorraria Multiplayer Roadmap (version 2)

Compiled from the ten survey steps plus a delta review of the later commits (step 11) (ModSystems, ModPlayers, Globals, BaseMachine + tile entities, UI, carts, liquids, content, remaining files, non-code surfaces). Every finding ID below (X1, G0, M1, U1, C1, P1, I1, R1, S1, A1 ...) refers to the matching sub-report; the full text is in the appendix file `FACTORRARIA_MULTIPLAYER_SURVEY_APPENDIX.md`.

Survey base: GitHub commit `25510ef` (183 `.cs` files). **Version 2** also covers every commit through `49f8da0` (2026-10-16, 192 `.cs` files). The code wins where it disagrees with this document.

---

## Revision history and what changed in version 2

- **Version 1** was written against commit `25510ef`.
- **Version 2** reviews the 29 commits from `25510ef` through `49f8da0` (28 new commits). They add the Robotic Arm machine (7 new files), the dynamic-draw framework (`IMachineDynamicDraw`, `MachineDynamicDrawSystem`), a new `BaseMachine.IntakeTiles()` hook, the arm's second mode on `MechanicalArmItem`, hardmode enemy lists for awakened statues, and recipe data changes. None of the original findings was invalidated; two statements were extended (the list of real-ModTile machines now includes the arm, and the machine count is one higher).

**Findings that changed the roadmap** (full text in appendix step 11)

| ID | Sev | What | Where it is applied |
|---|---|---|---|
| A1 | B | The arm worker only strikes after the client-only `RoboticArmVisual` reports it is in position; on a server the visual does not exist, so the arm never strikes | New patch 2.7 (prep) and Phase 7b.1 |
| A2 | B | Every world edit by the arm (pick, chop, wall, place, object placement) runs on the server with no network send | Phase 7b.2 |
| A3 | H | `RouteDrop` uses `IsOnScreen`, which is always false on a dedicated server, so every drop becomes a vItem even next to a player | Patch 2.7 (helper), Phase 7b.3 |
| A4 | H | The arm places tiles on the server and runs the placement hooks there; arm-placed machines are never broadcast, and tile-placed consumers must be callable from server code and idempotent | Phase 1.3, Phase 4.2, Phase 7b.6 |
| A5 | H | The area editor changes `AreaX/Y/W/H` on the client replica | Phase 5.1 (snapshot), 6.2 (accept filter), 7b.5 (request) |
| A5b | H | Clients need arm target and strike events to animate the visual | Phase 7b.4 |
| A6 | M | The arm item's place mode is a client-only item property switch; the server may reject the placement | Phase 7b.6 (verification item 15) |
| A7 | M | Dynamic-draw framework only works once machine entities exist on clients; detour is installed on servers too | Phase 0.5, works with Phases 4-5 |
| A8, A9 | L | `IntakeTiles()` default depends on the footprint geometry; `MachineUISystem.OpenMachine` must point at the live replica | Phase 4.1, Phase 6.1 |
| A11 | L | Statue entries hold asset references: included in the dedicated-server boot check (hardmode lists themselves are MP-safe) | Phase 0.5 |
| A12-A14 | L | Ghost `Player` `whoAmI`, drop capture `OnSpawn`, worker state: verify, no redesign | Phase 7b.3, 7b.7, verification items 17-18 |
| A10 | L | Recipe data changes | none |

**Recommendation:** land patch **2.7** before more arm development. It is a single-player-safe refactor, and every later arm feature then builds on logic that does not depend on the client.

**New default (change if you disagree):** the arm's animation on clients is driven by two small events from the server (target changed, strike started), not by re-simulating the worker on each client.

## 1. Goal and success definition

Make Factorraria work in multiplayer on **dedicated servers and Host & Play**, with single-player behavior unchanged.

The mod is "done" for multiplayer when all of this holds with a server and at least two clients:

1. Every machine can be placed, opened, operated and broken by any player, and everyone sees it working (animation, lights, progress, tanks).
2. Conveyor items, chest conveyors, pipes, motors, wires and the power grid behave identically for everyone.
3. Carts can be placed, driven by the world, loaded, fueled and picked up by any player, and everyone sees them move smoothly.
4. Recipe knowledge (world-shared), parchments and the recipe book work for everyone.
5. A player who joins late sees the complete current state; leaving and rejoining loses nothing.
6. Saving, shutting down and reloading the server keeps all of it.
7. No item duplication or loss through UI races, double handling or disconnects.

## 2. Decisions and assumptions

**Decided by you**
- Recipe knowledge is **world-shared**.
- Carts are **server-authoritative with client interpolation**.
- Targets: **Host & Play and dedicated server**.

**Adopted as defaults (change any of them before the phase that uses it)**
- Machine/cart slot edits: **Option A** (client predicts, sends the edit with the old item it expected; server applies only if the slot still matches; otherwise rejects and the client rolls back). Used in Phase 6 and Phase 9.
- Machine and cart UIs close when the player is out of tile reach, dead, or the target is gone.
- Tunables (defaults): cart update rate 15/s, cart interest radius two screens, interpolation buffer 100 ms, machine light-update rate limited, world-liquid broadcasts capped per tick. All live in one server-side config (Phase 1).
- World-shared "seen items" means one player holding an ingredient reveals the recipe for everyone.

**Design assumption to confirm early:** whether Host & Play runs the server in the same process or a separate one is unconfirmed. The plan is written to be correct either way: server logic is gated by `netMode != MultiplayerClient`, client-only logic by `!Main.dedServ`, and every request helper must run the server handler directly in single-player.

## 3. Working rules for every patch

1. **Server owns simulation.** Anything that changes shared state runs where `netMode != MultiplayerClient`.
2. **Requests, not edits.** Clients send a small request; the server validates (target exists, player in reach, state allows it, values sane), applies, then broadcasts. Rejections must leave the client consistent.
3. **Single-player short-circuit.** The request helper calls the server handler directly when `netMode == SinglePlayer`, so single-player never depends on the network path.
4. **Owner gating.** Code that reads local input, `Main.MouseWorld`, `Player.tileTargetX/Y` or spawns something once must check `player.whoAmI == Main.myPlayer`.
5. **Stable identifiers on the wire.** Recipe keys, liquid registry ids, skin keys, cart ids and vItem ids; never list indices.
6. **Three state channels.** Snapshot (on join), delta (on change), detail (only to players who have a UI open).
7. **Reuse existing helpers** instead of re-implementing them.
8. **Patch workflow unchanged.** Each step ships as a patch script (`patch_mp_<phase>_<name>.ps1`) through the existing engine with dry run first. After every patch I will give you a short "what changed / what to remember" list and a "things to test" checklist. Commit and push (including the regenerated `CODEBASE_INDEX.md`) after each successful patch.
9. **New folder `Common/Net/`** holds all packet code so the indexer and the project layout stay clean. Add `docs\*` to `buildIgnore` if you commit these documents to the repo.
10. **Machine logic must not depend on anything client-only** (visuals, `Main.screenPosition`, `Main.LocalPlayer`, textures, UI state). Server logic needs its own timing and its own "is a player near" test. Any new Robotic Arm work should follow this rule from now on (A1, A3).
11. **Build before you test.** A compile error does not stop tModLoader from loading the previous good build, so a test after a failed build tests old code. Check that the build output shows no errors (and, for a fix, that the new behavior is really in game) before reporting test results. `Player` has no `netUpdate`; to send the owner's player state use `FactorrariaNet.SyncPlayerNow(player)`.

## Phase 1 - Net foundation

**Goal:** the shared plumbing every later phase uses. Covers X1, X2, X3 and the "missing plumbing" list from step 2.

**Patches**
- **1.1 Net core:** `Common/Net/` with a packet-type enum, a router registered from `Factorraria.HandlePacket`, helpers (`IsServerSide`, `HasLocalClient`, `IsOwner(player)`, reach check, "send to players near a point", item write/read via the item serializer so prefix and mod data survive), and the request helper with the single-player short-circuit. Include a ping packet for testing.
- **1.2 Player sync and join sync:** a ModPlayer with `OnEnterWorld` (request full state), `PlayerDisconnect` (cleanup hook list), `SyncPlayer`/`CopyClientState`/`SendClientChanges` stubs. A **join-provider registry**: each system registers a provider that can write and read its full state; the server sends providers one at a time (chunked if large). Note: `ModSystem.NetSend/NetReceive` is called on *every* world-data send (join, boss kill, new day) and must be overridden as a pair, so it is only suitable for tiny state; large state uses the join-request path.
- **1.3 Tile-placed request (G0):** one client-to-server packet (position + tile type) sent from a single shared hook, with a consumer registry (`ITilePlacedConsumer`) so each system declares what it does when the server is told a tile was placed. Server validates the tile at that position matches and the sender is in reach. This is the one mechanism that fixes chest conveyors, liquid topology, awakened statues, pipes, motors, priority conveyors and machine placement. The consumer API must also be callable **directly from server code** (the Robotic Arm already places tiles on the server and triggers these hooks there, A4), and every consumer must be **idempotent** so a double notification from two paths is harmless.
- **1.4 Server-side network config and rate limiter:** a `ServerSide` `ModConfig` for the tunables in section 2, plus a per-player request rate limiter used by all handlers.

**Test checklist:** ping round trip client-to-server-to-client; late-join test with a dummy provider that sends a counter; tile-placed log appears on the server when a client places a block; single-player ignores all packets and still works; kicking/leaving fires the disconnect hook.

**Exit criteria:** the three mechanisms (request, join sync, tile-placed) demonstrably work in a server + 2 client session.

**Net core API (added by patch 1.1, all in `Common/Net/`; later patches build on this)**
- `FactorrariaPacket` (explicit byte ids, append only), `PacketDirection` (`ToServer` / `ToClient`) and `PacketHandler(BinaryReader reader, int sender)`. For `ToServer` packets `sender` is the player index, or `-1` when server code made the request itself (for example the Robotic Arm worker). For `ToClient` packets it is always `-1`.
- `FactorrariaNet.Register(type, direction, handler)` from a `ModSystem.Load()` on every side. `Factorraria.HandlePacket` forwards to `FactorrariaNet.Handle`, which drops unknown ids and packets that arrive on the wrong side, and catches every exception so a bad packet cannot crash the server.
- `FactorrariaNet.SendRequest(type, write)`: on a client it sends the packet; in single-player and from server code it runs the server handler right there through the same write/read path.
- `SendToClient`, `Broadcast`, `SendToNearby(center, radiusTiles, ...)`: do nothing unless this is a dedicated server (in single-player the server state already is the player's state).
- Helpers: `IsServerSide`, `HasLocalClient`, `IsSinglePlayer`, `IsOwner(player)`, `InReach(player, tileX, tileY)` (vanilla tile range + block range + held item boost + `ReachSlackTiles`), `WriteItem` / `ReadItem` (vanilla item serializer: stack, prefix and mod data survive), `Log`.
- Every handler must validate its input (target exists, reach, state, value ranges) and must read exactly what the writer wrote. `/fping` is the test command (a Chat command, so it runs on the client that typed it).

**Join sync API (added by patch 1.2, all in `Common/Net/`)**
- `JoinSync.Register(key, serverWrite, clientRead)` from `ModSystem.Load()` on every side. `key` is a short stable string and is what identifies the provider on the wire (never a list index). `serverWrite` runs on the server and must write the system's complete state; `clientRead` runs on the client, must read exactly what was written and must replace local state (a second request, such as `/fjoin`, runs it again).
- Flow: `FactorrariaPlayerSync.OnEnterWorld` calls `JoinSync.RequestFullState()` -> `JoinRequest(token)` -> the server queues one job per player and, from `JoinSyncSystem.PostUpdateEverything`, serializes one provider at a time and sends one chunk per tick (`JoinSync.ChunkSize`, 6000 bytes) -> `JoinChunk` -> `JoinDone` (provider count, byte count). The client reassembles each provider, calls its reader, then sets `JoinSync.Completed` and raises `JoinSync.JoinCompleted` (UI that depends on synced state can rebuild there). The log line `[MP-Net] join sync #N: ...` lists any provider that did not arrive.
- Guards: one job per player at a time, `RequestCooldownTicks` (120) between requests from the same player, stale tokens dropped, `MaxProviderBytes` cap, a provider that throws is skipped and reported as missing, and a reader that does not consume exactly the bytes written is logged. The tunables now come from `NetworkConfig` (patch 1.4).
- Single-player: the request handler only logs, nothing is sent, `JoinSync.Completed` is true immediately and no provider runs.
- `JoinSync.RegisterDisconnectHook(Action<int> playerIndex)`: runs from `ModPlayer.PlayerDisconnect()` on the server and on remote clients (tModLoader's documented behavior). The disconnecting player's join job and cooldown are cleared first. The mech suit arms (2.1), cart panels (Phase 6/9) and pending requests (Phase 10) register their cleanup here.
- `FactorrariaPlayerSync` (ModPlayer) holds `OnEnterWorld`, `PlayerDisconnect` and empty `SyncPlayer` / `CopyClientState` / `SendClientChanges` stubs for per-player state that other clients need later.
- Temporary test providers `test-counter` (a counter that increases on every full-state generation) and `test-blob` (20000 bytes with a checksum, so it needs four chunks) live in `JoinSyncSystem`; remove them in Phase 10. `/fjoin` re-requests the state and prints the summary in chat.

**Tile-placed API (added by patch 1.3, all in `Common/Net/`)**
- `ITilePlacedConsumer { bool AppliesTo(int tileType); void OnTilePlaced(int x, int y, int tileType, int placer); }`, registered with `TilePlaced.Register(consumer)` from `ModSystem.Load()` on every side. Consumers run only where the simulation runs (single-player, the server), never on a multiplayer client, and must be **idempotent**: the same placement can reach a consumer twice. `placer` is the player index, or -1 for server code or single-player.
- The single shared hook is `TilePlacedGlobalTile.PlaceInWorld`. Systems must NOT add their own `PlaceInWorld` hooks for this; patch 3.3 moves the existing ones (chest conveyor, liquid topology, awakened statues, pipes, motors, priority conveyors, machine placement) into consumers.
- On a multiplayer client the hook sends `TilePlaced` (x, y, tile type). The server (`TilePlaced.HandleRequest`) checks the position is in the world, the type is valid, the tile at that position is that type, and the sender is in reach (`FactorrariaNet.InReach`), logs a rejection otherwise, then runs the consumers. In single-player and on a server the hook runs the consumers directly (after the same tile check).
- Server code that places tiles (the Robotic Arm) needs nothing extra: it already calls `TileLoader.PlaceInWorld`, which reaches the hook. Other server code can call `TilePlaced.RunConsumers(x, y, tileType)` directly.
- Temporary test consumer `PlacementLogConsumer` in `TilePlacedSystem` logs `[MP-Net] tile placed: ...` for every placement (`TilePlacedSystem.LogPlacements`); remove it in Phase 10. Requests are rate-limited per player by `FactorrariaNet.Handle` (patch 1.4).

**Network config and rate limiter (added by patch 1.4)**
- `NetworkConfig` (`Content/Configs/NetworkConfig.cs`, `ConfigScope.ServerSide`) holds every multiplayer tunable. Read it as `NetworkConfig.Current.<Field>` at the point of use (never cache it in a field or constant), so a change in the config UI applies at once. In use now: `ReachSlackTiles` (`FactorrariaNet.ReachSlackTiles` reads it), `RequestsPerSecond` (40, 0 = off), `RequestBurst` (80), and the three join sync values. Reserved for later phases: `CartUpdatesPerSecond` (15), `CartInterestRadiusTiles` (200), `CartInterpolationBufferMs` (100), `MachineStateUpdatesPerSecond` (4), `LiquidBroadcastsPerTick` (20). The last two numbers and the radius were chosen when the config was written (the roadmap only fixed the cart rate and the buffer), so revisit them in the phase that uses them.
- `NetRateLimiter` is a per-player token bucket. `FactorrariaNet.Handle` charges every ToServer packet before its handler runs and drops it when the bucket is empty, with one summary log line per second (`[MP-Net] rate limit: dropped ...`). `FactorrariaNet.Register(type, direction, handler, cost)` takes an optional token cost (default 1) for expensive packets. Server code that calls `SendRequest` itself, and single-player, bypass it. The bucket resets when the player disconnects (through `JoinSync.RegisterDisconnectHook`).
- A handler still has to validate its input; the limiter only bounds how often. `/fflood [count]` is the test command (sends many pings in one tick).
- Known harmless warning: a packet dropped by the limiter never has its body read, so tModLoader logs `[tML] Silently Caught Exception: Read underflow N of M bytes caused by Factorraria in HandlePacket` on the server (seen in the 1.4 flood test). tModLoader catches it and the next packets parse normally. Only appears during a flood. Fixing it needs the body length, which HandlePacket does not receive; leave it unless it becomes noisy.
- Flood test numbers (cost 1, burst 80, 40/s): the first 80 pings of one tick were handled, the rest dropped, and `/fping` worked again afterwards. The drop summary logs the first drop immediately, so its count ("dropped 1") under-reports the real number; later drops are only logged if the flood continues past one second.

- Problem 3, cause corrected: vanilla adds gravity (`velocity.Y += gravity * gravDir`) before `PreUpdateMovement`, so `Player.gravity = 0f` set there has no effect (and the owner's own `gravity = 0` in `ApplyFreeMovement` is dead code; what keeps the owner hovering is its velocity overwrite, so that line was left alone). The remote copy now sets `Player.gravity = 0f` in `MechSuitPlayer.PostUpdateRunSpeeds` (after the run speeds, before gravity), only for a non-owner whose mirrored flag is set, and nothing else on it is touched. Vanilla's player packet (message 13) carries the control bits, the position and the velocity (velocity only when it is not zero), and the remote copy keeps extrapolating from those.
- Problem 2: while `netMode == MultiplayerClient` the owner sets `Projectile.netUpdate = true` on its live arms every `ArmResyncTicks` (180 ticks). Vanilla then sends the projectile (message 27) to the server, which relays it; a client without that arm creates it, a client that has it re-applies the same anchor and position. If the suit flag reaches the joiner after the arm, that copy ends on its first tick (flag still false) and the next re-send recreates it, so the worst case is about 3 seconds.
- `SyncPlayer` check: vanilla calls it from `SyncOnePlayer(plr, toWho, fromWho)` with `toWho` = the joining client, after the player info packets, so the flag should arrive before the first re-sent arm. The server logs `[MechSuit] sent suit flag of player X to joining client Y` when it sends it (temporary test line, remove in Phase 10).
- Hook order to remember for later owner-gating patches (2.2, 2.4): `ModPlayer.PreUpdateMovement` runs after vanilla's jump block and after gravity has been applied. To change gravity use a hook before it (`PostUpdateRunSpeeds`); to detect a key press from `controlJump`, compare with the previous frame yourself instead of reading `releaseJump`.

**Conveyor physics (added by patch 2.5)**
- Authority: players move themselves. Only the process that owns a player pushes it (`FactorrariaNet.HasLocalClient` and `Main.myPlayer`), so a dedicated server pushes no player and a client never pushes a remote copy. Vanilla only sends a player's position when a key changes, so while the belt moves the owner the system calls `FactorrariaNet.SyncPlayerNow(player)` (multiplayer client only; a no-op in single-player and on the server). NPCs: only `FactorrariaNet.IsServerSide` pushes them (single-player or server); on a server, a carried NPC gets `netUpdate = true` every `ConveyorPhysicsSystem.NpcSyncTicks` ticks (4, staggered by NPC index) so clients see a slide, not a jump. Clients never push NPCs. Items: unchanged, every side pushes them, the same as vanilla's own belts.
- `TryApplyConveyorForce` returns true only when the entity really moved (a wall blocked it, or it was not grounded, returns false), which is what triggers the sync, so a player standing on a blocked belt sends nothing extra.
- Known limits: the owner's push is 2.5 px per tick and its packet goes out every tick it moves (same cost as the Mech Suit); NPC sync is every 4th tick, so a fast belt may look slightly steppy on clients (raise or lower `NpcSyncTicks`). A boss or a town NPC with its own netUpdate pattern is unaffected.
- **2.5b correction (supersedes the NPC and item rules above):** the 2.5 test showed that NPCs were not carried and dropped items stayed put and jittered. Items were pushed by every side and corrected by server packets, and the NPC `netUpdate` flag did not get the carried NPC to the clients. New rule for both: only `FactorrariaNet.IsServerSide` pushes NPCs and dropped items; clients never do. The server sends the carried entity itself with `NetMessage.SendData(MessageID.SyncNPC / SyncItem, ..., index)` every `NpcSyncTicks` / `ItemSyncTicks` (3) ticks, staggered by index; instanced items are not sent (vanilla uses another message for them). The local player is unchanged. The server logs `[MP-Net] [Conveyor] last 5 s: NPC pushes N, item pushes M, sync packets sent K` while anything is carried (temporary, `ConveyorPhysicsSystem.LogStats`, remove in Phase 10). If NPCs or items still do not move, that log line says whether the server pushed anything (N and M above zero) and sent it (K above zero): zero pushes means the server's own check fails; pushes with packets means the clients are ignoring or overwriting them.
- **Open problem: conveyor NPCs and items (status after 2.5b, 2026-10-18).** Players on belts work (2.5). Not solved: (a) NPCs are not carried on a server + client session, (b) dropped items move but jump sporadically. Nothing is confirmed about the cause. What is known: the hook `PostUpdateNPCs` runs on every side (checked in tModLoader's Main patch); 2.5b made only the server push NPCs and items and send them with `SyncNPC` / `SyncItem` every 3 ticks, and the clients no longer push them; the old 2.5 variant (everyone pushes items) jittered and did not move them. Not yet known: (1) whether NPCs are carried in SINGLE-PLAYER on each belt type (never reported); (2) which belt was used: `TryApplyConveyorForce` only moves NPCs on the two priority conveyors (`if (!(entity is Item)) break;`), on vanilla belts NPCs are left to vanilla; (3) the server's `[MP-Net] [Conveyor] last 5 s: NPC pushes N, item pushes M, sync packets sent K` lines (temporary, `ConveyorPhysicsSystem.LogStats`).
  - Hypotheses, untested, in the order to check them: A) the server never pushes the NPC: its `velocity.Y` at rest can stay above the 0.2 grounded limit, or the NPC's own AI undoes the move; the log's N would be 0. B) the server pushes but the clients ignore or overwrite it: a client NPC runs its own AI and may snap back, or the packet does not carry what is needed (N and K above 0 but nothing moves). C) the items jump because one push is 2.5 px per tick and an item is sent every 3 ticks (7.5 px steps), because vanilla also sends the item on its own schedule, and because a client copy keeps its own velocity and friction between packets; vanilla belts may also push items by themselves on every side (a double push on vanilla belts). D) timing: our push happens in `PostUpdateNPCs`, after vanilla's own NPC and item update and its sync decision for that tick.
  - Ideas for a fix, not tried: send velocity so the client extrapolates; push NPCs by velocity.X instead of position; let clients run a cosmetic-only copy of the push and take only large corrections from the server; or leave carried dropped items as they are and let Phase 7 solve them (items on belts are meant to become virtual items there, which are simulated on the server and interpolated on clients, so the item jitter may be better fixed once, in 7.1 and 7.2).
  - Result (2026-10-18, server log + single-player tests): (1) single-player: NPCs ARE carried on both priority conveyors and were NOT carried on vanilla belts, same on a dedicated server, so there was no netcode bug behind the NPC report; the cause was the `entity is Item` check. (3) the server log showed `NPC pushes 600, item pushes 0, sync packets sent 200` per 5 s for two NPCs: the server pushes every tick and sends every 3 ticks, so hypothesis A is refuted (B and D are not needed unless an NPC on a priority conveyor looks bad on a client; to confirm). Fix: patch 2.5c removes the check for NPCs. Dropped items: on vanilla belts they move but jump (hypothesis C, kept as is, cosmetic); on priority conveyors they are not pushed by `ConveyorPhysicsSystem` because `VirtualItemSystem.ConvertItemsToVItems` turns them into virtual items, and an item that vanishes when another of the same type is dropped there was reported (not checked in single-player yet). `VirtualItemSystem` has no `netMode` guards, so the server and every client convert and simulate their own separate vItem lists. Decision: leave the items to Phase 7.1 and 7.2 (see the Phase 7 additions), do not patch them here.
  - 2.5c test checklist: single-player: a zombie (or any grounded NPC) on a vanilla belt right and left is carried, still carried on both priority conveyors, a player on a vanilla belt moves at vanilla speed (no double push), critters, slimes and flying NPCs near belts do not behave oddly; dedicated server + client: the same zombie on a vanilla belt and on a priority conveyor is carried on the client screen without stutter or snap-back (if it stutters, write 2.5d for hypothesis B: send velocity and let the client extrapolate).

**Custom wires (added by patch 3.1)**
- Authority: the server owns `CustomWireSystem.WireGrid` (the power grid is built there). `CopperWireItem`, `TinWireItem` and the two cutters run only for the owner (`FactorrariaNet.IsOwner`), because `Player.tileTargetX/Y` is the local mouse tile; every other copy of the player returns `null` and does nothing. **Server-safe geometry (added by patch 4.1)**
- Authority: geometry is derived data, not synced. Every process computes the same numbers from the same `TileObjectData`, so nothing goes on the wire. `BaseMachine.InitializeGeometry()` sets `cornerPosition` (= `Position`, the entity always sits at the top-left tile), `MachineWidth/Height` (from `GetTileData(ValidTileType, 0)`, no world tile needed) and `MachineCenter`, then `MachineInitialized`. It returns false and stays uninitialised (retried next call) while the position or the tile data is unusable.

- Server log: `[Machines] geometry initialised: <Type> at (x, y) WxH` once per machine on a dedicated server (temporary, remove in Phase 10).
- 4.1 test checklist: single-player: machines still take items from a conveyor under them and push finished items onto it, the Robotic Arm and drawing are unchanged, no new errors. Dedicated server (the server only runs its update loop while a client is connected): after joining, the server log has one `[Machines] geometry initialised` line per machine with the right size (furnace 3x2 and so on, compare with the tile) and the `[MP-Boot]` probe summary now reports geometry initialised equal to the machine count (it was 0 of 79 in Phase 0); a conveyor under a machine on the server: report whether vItems feed and leave the machine (the conveyor itself still only simulates correctly on the server after Phase 7, so a failure there is not a 4.1 bug, but report what you see); no errors in the server console or the client logs.

**Machine placement (added by patch 4.2)**
- Authority: the server (or single-player) creates every machine entity; a client never does. One helper, `MachinePlacement.ServerPlace(tileType, x, y)` in `Common/Net/MachinePlacement.cs`, creates the entity through the existing `GetOrCreateEntity` (Place, power grid registration, liquid rebuild flag), runs `OnPlaced`, and on a dedicated server shares it with vanilla message 86 (`MessageID.TileEntitySharing`: entity id + position, so both sides use the same id). It returns the existing entity untouched when there is one, so every route can call it more than once.
- Route 1, ModTile machines (motors, Mechanical Assembler, Robotic Arm): `BaseMachine.Hook_AfterPlacement`. A multiplayer client sends `SendTileSquare` and the tile-entity placement request (message 87, exactly like tModLoader's `Generic_Hook_AfterPlacement`) and returns -1. The server's `NetPlaceEntityAttempt` (now overridden: it refuses when a machine is already at that position or the tile is not valid there, because the base version would place a second entity) places the entity, `OnNetPlace` runs `OnPlaced` and the registration, and tModLoader sends message 86. Single-player and the server (the Robotic Arm calls the hook on the server) call `ServerPlace` directly, which also fixes A4 for ModTile machines (the arm's machine now reaches the clients).
- Route 2, vanilla-tile machines (furnace, hellforge, autohammer, extractinator, solidifier, gel burner, decay chamber, ice machine, liquid distillator, materializer): `MachinePlacedConsumer` (registered in `TilePlacedConsumersSystem.Load`, applies only to vanilla tile ids that are in `MachineVisualRegistry`). It runs on the server and in single-player when the client's `TilePlaced` request passes its checks, and for server-side placements through `TileLoader.PlaceInWorld` (Robotic Arm). `MachineVisualOverride.PlaceInWorld` was removed.
- Lookup-only on a multiplayer client: `MachineVisualDefinition.ResolveEntity` is `FindEntity` on a client and the old get-or-create everywhere else. `PreDraw`, `ModifyLight`, `RightClick` and `KillTile` use it; a client without an entity for a machine tile draws the plain vanilla tile, shows no UI and does nothing. Single-player still creates a missing entity on demand (draw code) until patch 4.5 adds the bootstrap scan, so existing saves keep working.
- Server log: `[Machines] placed <Type> at (x, y), id N` (and `(client request)` for the ModTile route). Temporary, remove in Phase 10.
- Known limits: the entity a client receives is empty (no slots, tanks or flags) until Phase 5, so a freshly placed machine shows its Off sprite and an empty UI on every client; world-generated or older machine tiles that have no entity on the server (a Hellforge from worldgen, tiles placed before this patch) have none on clients either until patch 4.5; killing a machine as a client is still unreliable until 4.4 (the server's `KillTile` runs the old get-or-create path); biome is still `Unknown` on the server until 4.3; the entity is only shared with clients that are in the world when it is created (a client joining later gets it through the vanilla section data).
- 4.2 test checklist: single-player: place each machine type (furnace, hellforge, a motor, the Mechanical Assembler, the Robotic Arm, a materializer): it works as before, power and pipes connect, break and re-place, save and reload; place a vanilla-tile machine on a conveyor and check it takes items. Dedicated server + client: the client places a furnace (vanilla tile) and a motor / assembler / arm (ModTile): the server logs one `[Machines] placed` line per machine (never two for the same position) and the client keeps seeing the machine and can right-click it (an empty UI is expected); a second client sees the same machines; place two of the same machine quickly: two entities, no duplicates; leave and rejoin: machines are still there; stop and restart the server: machines are saved and come back; the Robotic Arm places a machine (a furnace and a motor) on the server: the clients get the entity too; no phantom entities on the client (check with `/fjoin` and the `[MP-Boot]` probe: entity counts on server and client match for the machines in range); no errors in the server console or the client logs.

**Placement info (added by patch 4.3)**
- Authority: the server owns `BaseMachine.InsideBiome` (it is saved in `SaveData`, used by `ResolveIncomingLiquid` and the Ice Machine, all server logic). Only the placing client can detect the biome (it reads the local player's Zone flags, a dedicated server has no local player), so the client reports it: packet `MachineBiomeReport` (18, ToServer): `short x, short y, byte biome`. The server never trusts more than the enum value: it checks the sender, the bounds, that the biome is a defined `MachineBiome`, that a tile exists there and that the sender is in reach, and only applies it to a machine that is still waiting for its report.
- Client routes (one send per placement): ModTile machines send it at the end of the client branch of `BaseMachine.Hook_AfterPlacement` (after the tile square and the entity placement request); vanilla-tile machines send it from the client branch of `TilePlaced.NotifyPlaced`, after the `TilePlaced` request, only for tile ids that are in `MachineVisualRegistry`. Single-player and the server send nothing: `OnPlaced` still calls `DetermineBiomeAt` itself.
- Server state (`MachinePlacementInfo`, in `Common/Net/MachinePlacementInfo.cs`): `awaiting` (entity created in `OnPlaced`, report not received) and `early` (report received, entity not created yet), each capped at 256 entries and pruned after 600 ticks once a second. Both orders work, so a reordered or slow packet does not lose the value; a duplicate or late report for a machine that is no longer waiting is logged and ignored, which also stops a client from changing the biome of an old machine.
- Known limits: a machine placed by server code (the Robotic Arm) keeps `Unknown` because no client reports for it (proposed fix for later: take the biome of the nearest active player on the server, or scan the tiles around the machine); clients do not have `InsideBiome` on their replica until patch 5.1 adds it to the entity snapshot; the biome is the placer's biome at the moment of placement, the same rule as in single-player.
- Server log (temporary): `[Machines] biome <b> applied to <Type> at (x, y) (reported by <name>)` or `(report arrived first)`, plus `rejected` / `ignored` lines.

**Kill path (added by patch 4.4)**
- Authority: the server (and single-player) owns a machine's contents and its entity. A broken machine tile runs `MachineVisualOverride.KillTile` in every process that sees the break (the breaker, the server, every other client), so the hook now branches on the side: server and single-player drop the contents once and remove the entity (`MachineRemoval.OnTileKilled` in `Common/Net/MachineRemoval.cs`); a multiplayer client only removes its replica and drops nothing. No new packet: vanilla already broadcasts the tile removal, and each client's own hook removes its replica (the same mechanism vanilla tile entities rely on).
- `fail` and `effectOnly`: `KillTile` is a damage hook too, so it now ignores those two cases and only acts when the tile is really breaking. The Robotic Arm's `WorldGen.KillTile(x, y, fail: true)` hits therefore no longer touch the machine.
- UI: `BaseMachine.OnKill` still calls `NotifyMachineKilled`, which closes the open UI on the client whose replica is removed by its own hook. As a safety net `MachineUISystem.UpdateUI` closes the UI on a multiplayer client when the open entity is no longer in `TileEntity.ByID`. The subscriber-list part (closing the UI for clients that have it open, from the server) belongs to the detail channel, patch 5.3.
- Known limits: a tile without an entity (world-generated machine tiles before patch 4.5) has nothing to drop and nothing to remove; liquids inside tanks are lost on break as before; contents on a dedicated server are normally empty until patches 6.2 (slot edits) and Phase 7 (conveyor intake), so a drop can only be fully tested in single-player for now.
- Server log (temporary): `[Machines] removed <Type> at (x, y), id N, dropped K stack(s)`.

**Entity bootstrap (added by patch 4.5)**
- Authority: the server and single-player own entity creation; a multiplayer client never creates one (it receives them through message 86, or with the vanilla section data when it joins later). Draw and light code are lookup-only in every process now (`MachineVisualDefinition.ResolveEntity` calls `FindEntity`), so single-player no longer creates entities from draw code.
- `MachinePlacement.EnsureEntity(x, y)` is the one "find or create" helper for an existing machine tile (any tile of the machine): lookup, then (server / single-player only) check that the tile type has object data and that the corner tile is the same machine tile, create through `GetEntity`, `InitializeGeometry`, `Share`. It is idempotent and does not run `OnPlaced` (biome stays Unknown, nobody placed it). Call it from anything that needs an entity for a tile that may have none: the right-click handler already does, and the Phase 6.1 open-machine request must. Pipe, wire and conveyor adjacency checks stay lookup-only on purpose (creating entities inside a flood fill would change the lists being walked); the scan makes them complete within seconds of the world loading, and every creation sets the power and liquid rebuild flags.
- Scan (`MachineBootstrapSystem`, `Common/Net/MachineBootstrapSystem.cs`): started by `OnWorldLoad` on the server and single-player, run from `PostUpdateEverything`, `ColumnsPerTick` (150, a plain static so it can be tuned) world columns per tick, a lookup table of registered machine tile types so non-machine tiles cost one array read. It also covers a world that has just been generated. A dedicated server only updates while a client is connected, so the scan starts with the first join.
- Known limits: bootstrapped machines have biome Unknown (proposal for later: a server-side detection from the tiles around the machine); a client that is already in the world gets bootstrapped entities through message 86, one that joins later through the section data; the scan runs once per world load, so a machine tile created later by something that bypasses the placement hooks (another mod, a console command) is only caught by `EnsureEntity` on right-click.
- Server log (temporary): `[Machines] bootstrapped <Type> at (x, y), id N` and `[Machines] bootstrap scan done: ...`.

**Test checklist:** place each machine type as a client on a dedicated server; the server log shows one entity per machine with correct size/center; machines placed via the ModTile path and via the vanilla-tile path both work; break a machine as a client and as the host: contents drop once, entity is gone on server and every client; save and reload keeps machines; world-generated Hellforge and furnaces get entities after load; conveyors can feed and pick up from machines on the dedicated server (geometry fix); biome-dependent recipe behaves according to the placer's biome.

## Phase 5 - Machine sync

**Goal:** every client has an accurate replica of each machine. Covers M3, M7, M8, M9 and the sync half of U3. Pairs with Phase 4.

**Patches**
- **5.1 Snapshot:** `NetSend/NetReceive` for `BaseMachine` and subclasses (slots, tanks, flags, geometry, selected recipe by stable key, Materializer `BackgroundActive`, motor `Facing`, fuel state, Robotic Arm `AreaX/Y/W/H`). tModLoader sends it with the section/entity data; recipe and liquid references use stable keys/ids.
- **5.2 Light updates:** a compact, rate-limited packet for `isOn`, `isWorking`, work progress, crafts counter, `useFraction`, fuel burn fraction, and quantized tank type/amount for overlays, sent only to players near the machine and only when changed. Receiving clients update the replica and animation/light follow automatically (animation callbacks are draw-driven and already run only on clients).
- **5.3 Detail channel:** server-side subscriber list per machine (add on open, remove on close, leave, death or out of reach; capped), sending full slot/tank contents on subscribe and after each accepted edit.
- **5.4 Power flags:** make sure the server writes `isOn`/`useFraction` from `PowerNetwork` and that those fields are part of 5.2; confirm wire sync (3.1) makes grids form on the server. Status (patch 5.4): confirmed by reading the code; one gap fixed (the one-time index of saved machines no longer depends on the machine list being empty); a `[Power] rebuilt` server log line shows the grids for the test.

**Test checklist:** machine animation, lights and fire effects work for a second player standing nearby; progress bar and output counter are correct for the player with the UI open; a player far away costs no light-update traffic; a late joiner sees correct state without opening anything; powered machines turn on and off together on all screens when a generator is added or removed; Hellforge infinite lava and Materializer state are visible to all.

**Machine snapshot (added by patch 5.1)**
- Authority: the server (or single-player) owns all machine state; a client replica is a read-only copy. 5.1 adds no packet and no request. tModLoader calls `BaseMachine.NetSend` on the server in two places and `NetReceive` on the client: with the tile section data (a client joins, or reaches a section it has not received yet) and with vanilla's tile-entity sharing message 86 (`MachinePlacement.Share`, used by the 4.2 placement routes and the 4.5 bootstrap scan). Both use the same bytes. In single-player neither is ever called, the world file keeps using `SaveData` / `LoadData`, and there is nothing to short-circuit.
- Source facts (tModLoader source, verified for patch 5.1): `NetReceive` runs on a NEW instance that replaces the entity at that position (Position is set, ID not yet when it is called in the section path), it may run on the network thread, and `TileEntity.Update` is not called on multiplayer clients. So a replica only changes when a new snapshot arrives; the live updates are 5.2 (light) and 5.3 (detail).
- Wire format (version 1): `Write7BitEncodedInt(length)` + payload. Payload: version byte, flags (isOn, isWorking), InsideBiome byte, WorkProgress, CraftsFinished, useFraction (electric machines only), manual recipe group key, running recipe key + position hint + content fingerprint, input slots, output slots, input tanks, output tanks, fuel modules (Remaining, Capacity), then the subclass extras. Slots are a presence byte plus `ItemIO.Send` with the stack. Tanks are `LiquidTypeRegistry` id + 1 and a float amount; the tank objects stay (their pipe filters) and only type and amount are overwritten. Recipe groups use `RecipeCatalog.KeyFor(machineName, group)`; the running recipe is found again in that group by fingerprint (FNV-1a over item internal names, stacks and liquid ids and amounts), with the position only as a hint, so a differently ordered recipe list still resolves.
- Coverage: BaseMachine fields cover Furnace, Hellforge, Ice Machine, Liquid Distillator, Decay Chamber, Solidifier, Autohammer, Extractinator, Mechanical Assembler and Gel Burner (useFraction for the electric ones). Extras: Motor MK1 (Facing, in `MotorTileEntityBase`), Magic Materializer (BackgroundActive), Robotic Arm (AreaX/Y/W/H, applied through `SetArea`). Not synced on purpose (server runtime state): the Materializer's awakened statue and enemy counts, the arm's worker, hand motion and visual, `wasOn`, `runningRecipe`.
- Interaction with 4.2 and 4.5: a machine created by the bootstrap scan is shared with its fresh default state (it had no entity, so nothing was lost) and biome Unknown. The placement share goes out before the placing client's biome report arrives, so `MachinePlacementInfo.Apply` re-shares the machine once the biome is applied; in the vanilla-tile route a report that arrives first is applied inside `OnPlaced`, which causes one extra identical share (harmless).
- Known limits: the replica is frozen at delivery until 5.2 and 5.3. A delivery replaces the object, so anything holding the old instance (`MachineUISystem.OpenMachine`, `CurrentEntity`) points at a dead copy until 6.1 re-resolves it by position. Slot clicks edit the client copy only until 6.2 and the next delivery overwrites them. Snapshot size is about 25 bytes for an empty machine and grows with contents (items carry their mod data); one section holds at most 1000 entities.
- Temporary test aid (remove in Phase 10): `/fsnap [all|share]` runs in the server console, a client's chat or single-player. It prints the counters (snapshots sent and received, bytes, failures) and one line per machine (type, position, id, size, flags, contents, tanks, fuel, recipe, extras, digest of the snapshot bytes). `fsnap share` (server console only) re-sends every machine with message 86.

**Machine light updates (added by patch 5.2)**
- Authority: the server (or single-player) owns all machine state; replicas are read-only. `MachineLightSyncSystem` (Common/Net/MachineLightSync.cs) runs only when `netMode == Server`, from `PostUpdateEverything`, so single-player and clients never send. Packet `MachineLightUpdate` (19, ToClient): format byte, entry count, then per entry `short x, short y, length, payload`. No request packet.
- What is sent (`BaseMachine.BuildLightState`, all quantized): flags (isOn, isWorking), work progress rounded down to `ProgressStepTicks` (10), `CraftsFinished`, use fraction as a byte (electric machines only), the running recipe as the 5.1 content fingerprint (0 = none; the client finds it again in its own recipe book, so `WorkFraction` and `GetFuelBurnFraction` work on the replica), every fuel module's Remaining and Capacity, and for every input and output tank the liquid type plus the amount in 1/32 of its capacity (an empty tank sends no amount, and the first non-empty step is 1). Not sent: slots (5.3), `ManualGroup` (6.3), biome (snapshot), motor Facing, Materializer BackgroundActive and the arm area (their own patches: 6.4, 8.3, 7b.5; until then they only change through the 5.1 snapshot).
- Who gets it: `ScanIntervalTicks` (6) ticks apart the server walks every `BaseMachine`. A machine is looked at only when an active player is inside `RangeHalfWidth` x `RangeHalfHeight` (1440 x 880 px, i.e. screen half size plus about 30 tiles) of its centre, measured from `Main.player[i].Center` (the server's synced copy, so it works on a dedicated server). It keeps a record per machine: the last payload, a version that goes up whenever the payload bytes change, and per player the version that player last received. A player is sent an entry when their version is older, so a change reaches only near players, a player who walks into range gets the current state on the next scan, a far player costs nothing, and an unchanged machine costs nothing. A slot that becomes inactive is reset (mark 0).
- Receiver (`MachineLightSync.HandleLightUpdate` -> `BaseMachine.ApplyLightState`): looks the machine up by position, writes the values into the replica and does nothing else (no `Share`, no replacement, no send). A tank or use fraction that still quantizes to the same value keeps its exact 5.1 snapshot value, so an idle machine stays identical to the server (`/fsnap` `digest=`). An entry for a position the client has no machine at is skipped (counted as missed).
- Interaction with 5.1 and 4.3: the snapshot stays the full state and the only way slots arrive; light packets follow it on the same ordered stream. The re-share after the biome report replaces the replica with a fresh snapshot and the light packets after it only carry changes. The server's per-player marks are not reset by a share: the share is at least as new as the last light packet, and a player who never got a light packet has mark 0 and gets one the first time they are near.
- Known limits: progress is rounded to 10 ticks, so a UI progress bar steps about 6 times per second until 5.3 sends detail to players with the UI open; tank levels are approximate (1/32) until 5.3; Materializer right-click still flips `BackgroundActive` on the client copy only (6.4); the replica's recipe is the first recipe in the book with that fingerprint (two recipes with identical content are treated as the same); a screen larger than the near rectangle (very high resolution, zoomed out) can show a machine edge that is not updating; Robotic Arm movement is its own channel (7b).
- Temporary test aid (remove in Phase 10): the light counters and the `light=` digest in `/fsnap`. `light=` is the digest of the light payload: it must be equal on the server and on a client for every machine that is not changing, and also for running machines apart from progress and fuel numbers that moved between the two listings.
- 5.2 test checklist: build first and confirm zero compile errors. Single-player: nothing changes (machines run, animate and light as before; `/fsnap` counters stay 0). Dedicated server + client: stand next to a running Furnace with coal and ore: its animation, light and dust run on the client, stop when fuel or ingredients run out and start when they come back; a powered machine (Autohammer, Solidifier, Mechanical Assembler) shows on and off together with the grid when a Gel Burner is added or removed (use fraction too: the electricity icon in a UI); a Gel Burner burning gel shows its fire; Hellforge and Ice Machine liquid overlays follow the tank; Materializer and motors show their state. `/fsnap all` on the client and `fsnap all` in the server console: the same `light=` for every idle machine, and for running machines only the prog, crafts and fuel numbers may differ. Counters: on the server `light: packets sent` grows only while machines near the client change; stop all machines and it stops growing. Far away: walk about 100 tiles away (or use a second client far from the machines): the packet count does not grow for that player. Walk back: machines show their current state within a moment. Join late: a second client that joins later sees machines with the right state (snapshot) and live changes (light). Second concurrent client: both see the same animations. Walk into a section the client had not received (fast travel by Recall or Magic Mirror far away and back): the machines there start animating once their section arrives (`missed` may go up a little, that is fine). Rejoin: state correct. Report bytes per second if it looks heavy: `light: ... B` over a known time.

**Machine detail channel (added by patch 5.3)**
- Authority: the server (or single-player) owns all machine state; replicas are read-only. `MachineDetailSystem` (Common/Net/MachineDetail.cs) runs its scan only when `netMode == Server`, from `PostUpdateEverything`, every `ScanIntervalTicks` (3) ticks. Single-player and the host never subscribe (`MachineDetail.SendSubscribe` does nothing unless the client is a multiplayer client): the entity is the state.
- Packets: `MachineSubscribeRequest` (20, ToServer: short x, short y, bool open), `MachineDetail` (21, ToClient: short x, short y, length-prefixed payload), `MachineDetailClosed` (22, ToClient: short x, short y, byte reason). x, y is the machine's corner (`entity.Position`).
- Subscribe: the server checks the sender (active, alive), that a `BaseMachine` exists at the position (any tile of the machine resolves to its corner), and reach to the nearest footprint tile (vanilla tile range, `ReachSlackTiles`, block range and the held item's tile boost). It drops the player's previous subscription (one machine per player), refuses when the machine already has `MaxSubscribersPerMachine` (8) subscribers (reason Full), adds the player and sends the full detail at once. A refused request (no machine, not in reach, full) gets `MachineDetailClosed` with reason Rejected or Full, so the client's UI closes.
- What is sent: `BaseMachine.BuildDetail`: flags, exact progress, crafts, use fraction (electric machines), manual group and running recipe (stable keys plus fingerprint, same codec as 5.1), every input and output slot (`ItemIO`), exact tank type and amount, fuel Remaining and Capacity. No biome and no subclass extras. The scan builds the payload for subscribed machines only, compares the bytes with the last payload, bumps a version when they differ and sends to every subscriber whose copy is older. So it covers changes from any cause (recipe progress, a finished craft, conveyor intake, later also other players' edits); an idle machine costs nothing. `MachineDetailSystem.Push(machine)` sends at once (6.2 calls it after an accepted edit).
- Receiver: `MachineDetail.HandleDetail` finds the replica by position and calls `BaseMachine.ApplyDetail`, which writes in place (slots are replaced item by item, tanks keep their objects) and sets `LastDetailTick`. For 30 ticks after a detail packet `ApplyLightState` returns early, so rounded light values never overwrite the exact ones.
- End of a subscription: the player closes the UI or opens another machine (client sends open or close), leaves (`FactorrariaPlayerSync.PlayerDisconnect` and a scan check for an inactive slot), dies (reason Dead), walks further than reach + `KeepReachExtraTiles` (3) (reason OutOfReach), or the machine is killed (`BaseMachine.OnKill` on the server calls `MachineDetailSystem.NotifyMachineKilled`, reason Killed, which also covers kills by the Robotic Arm; a scan check catches an entity that is no longer the live one). Every end except leaving and the player's own close sends `MachineDetailClosed`; the client handler only records the request and `MachineUISystem.UpdateUI` closes the UI on the main thread, without telling the server again. Since 5.3b a notice with reason OutOfReach does the full close (menu-close sound and `Main.playerInventory = false`, like clicking the machine again, plus the inventory); the other reasons (Killed, Dead, Full, Rejected) still close the panel silently. Since 5.3c the client also does that full close by itself when its own living player is further than reach + `KeepReachExtraTiles` from the open machine (`MachineUISystem.UpdateUI`, using `MachineDetailSystem.WithinReach`), so it no longer depends on the notice alone, and every client-side close of a machine UI logs a `[Detail]` line with its cause.
- Split with 6.1: 5.3 owns the transport and the server list. The request is thin on purpose. 6.1 extends it (EnsureEntity on open, one validation helper for the whole request family, the UI re-resolving the live replica every frame, client-side reach and death closing) and may fold it into the `MachineRequest` family; packet ids stay as they are. Until 6.1, a replica that is replaced while its UI is open (a re-share) still closes the UI through the 4.4 liveness check, and the client then sends the unsubscribe.
- Known limits: slot edits on a client change only its own copy until 6.2, and the next detail packet overwrites them (an item put into a slot on a client is lost); the UI shows server state only. Recipe picks (6.3) and the Materializer toggle (6.4) are not requests yet; the manual group in the detail packet overwrites a pick made on a client. The MP-only close at reach + 3 tiles has no single-player counterpart until 6.1 adds the client-side check. The Robotic Arm area drag is not touched by detail (no extras).
- Temporary test aid (remove in Phase 10): the `[Detail]` server log lines, the `MachineDetail` counters and `Describe()`, `DescribeSubscriptions()` and the detail part of the `/fsnap` summary (server console: subscription list and counters; client: received, applied, missed, failed, close notices).

## 9. Biggest risks

- **Phase 4/5 (machine framework):** every machine depends on it; mitigate by shipping geometry (4.1) first, testing in single-player after each patch, and doing 4 and 5 as one test unit.
- **Phase 7 (virtual items):** performance and consistency under load; mitigate with interest-based sending, deltas, and the profiling pass.
- **Phase 9 (carts):** biggest new code; mitigate by building replication (9.2) before any interaction (9.3) and testing interpolation on its own.
- **Phase 7b (Robotic Arm):** the worker was written against a client-side visual. The motion-model refactor (2.7) is the main risk, but it is single-player testable, so land it first; keep new arm features free of client-only dependencies (rule 10).
- **Item duplication through UI races:** mitigated by compare-and-swap edits, server-only drops and consumption on acknowledgement; each phase's test checklist includes a race test.

## 10. What stays untouched

Recipe registries and fuel tables, the `BaseMachine` recipe/fuel hooks, the thin machine subclasses, worldgen and chest loot, buckets, custom liquid definitions, materials, ores, joke items, the local recipe-book UI, `TimedCrafting*`, `ExtractinatorBlockPlayer`, and the client-only configs. Also unchanged: the arm's visual animation math (`RoboticArmVisual`, `MechanicalArmIK`), the dynamic-draw passes, the arm's tile-selection logic and the recipe data changes.
