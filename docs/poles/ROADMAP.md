# Power Poles: Development Roadmap

Factorraria power poles: two electric pole machines (wooden and platinum) joined by hanging wires. Written against repo commit `7d955cc`. Where this document and the code disagree, the code wins.

## 1. Decisions

### Fixed by Ismail
- Two variants. **Wooden**: 1 swaying crossboard with 2 connection points, footprint 1x14, overhang canvas 3x14 (footprint in the middle column, `originX: 1, originY: 0`; the canvas only holds the pixels that poke out left and right). **Platinum**: 2 swaying crossboards (upper and lower) with 2 connection points each (4 total), footprint 1x16, drawn through the overhang system too for consistency (canvas 1x16, `originX: 0, originY: 0`, 16x256 art).
- Custom `ModTile` machines, non-solid (walk-through), anchored on a solid tile below. Electric consumers with a small constant draw that models transport loss. No machine recipes. The only UI element is the electric icon.
- Each pole has a single texture (no On/Off look).
- **Crossboards (changed after P2).** Each board is ONE texture sheet (5 columns of equal cells, layout in the P6b Progress line; it was a single PNG per board until P6b), drawn manually by `PowerPoleCrossboardSystem` (client only, after tiles and after the overhang canvases), rotated around the board's centre by a wind sway (none at or below 20 mph, ramping up linearly to full at 60 mph; platinum sways at 50% of wooden; the swing phase comes from each pole's tile position), and also drawn on the placement hologram. A board is `PoleBoard(texturePath, size, poleHeightTiles, rowFromBottom, linkPoints)`: its centre sits on the middle of the pole column at that tile row, counted from the bottom (wooden row 12 of 14; platinum upper row 14 and lower row 12 of 16). Link points are pixels inside one cell of the board sheet (P6b). Links use the resting position (`GetLinkPointWorld`); only drawing uses the swayed one (`GetLinkPointWorldSwayed`).
- The footprint tiles accept ground wires (the existing `EnqueueMachineWires` already walks the footprint only). The overhang area accepts none.
- Gold wire becomes placeable like copper and tin. Copper and tin hanging wires have a shorter span than gold.
- Holding a wire (selected item or item on the cursor): click pole 1, a preview wire follows the cursor, click a different pole to connect. v1 draws a straight line. Later: Luminance pixelated trail, wind and player disturbance.

### Assumptions (change any of these before the patch that uses them)
- **A1. What a click means (decided 2026-10-26).** The footprint accepts ground wire with a **left** click, so linking is a **right** click while a wire item is held (selected item or item on the cursor). A right click on the pole's footprint, or on the hitbox of one of its crossboards, starts a link, and a right click on a second pole finishes it. Left clicks behave as today (ground wire on the footprint, nothing on the empty overhang area), so the wire items need no `CanUseItem` guard. The starting right click has no client-side reach check (removed in P6a after testing), so the player may click a pole at any distance; the pending wire follows the cursor as a hologram and the player may walk away. The finishing right click is checked by the server (the tile clicked on pole B must be on that pole; CHANGED in P7c: no reach check any more, client or server).
- **A2. Span is set by the wire item (decided).** Copper 20 tiles, tin 20, gold 40, measured between the two connection points at their resting positions. Public instance fields on `PoleLinkSystem` (`CopperSpan`, `TinSpan`, `GoldSpan`), not `const` or `static`, so hot reload can tweak them. A pending link (patch P6) turns red when it is longer than the span, cannot be committed, and is dropped at `BreakSpanMultiplier` (2) times the span: copper and tin 40 tiles, gold 80.
- **A3. Wire cost (decided).** One link costs `ceil(span / tilesPerItem)` wire items of its type: copper and tin 5 tiles per item, gold 8 (`CopperTilesPerItem`, `TinTilesPerItem`, `GoldTilesPerItem`). The items are taken when the link is committed (the second right click), never at the first click. The cost is stored in the link and refunded when it is cut or the pole is killed.
- **A4. Pole item recipes (decided).** Ismail registered the recipes himself. The machines have no `CustomRecipe`s and no pole patch touches the recipes.
- **A5. Draw.** Wooden 15 power, platinum 5 power (assembler 200, arm 100). Constant for v1. Optional length-scaled loss in P8.
- **A6. Vanilla wire toggling** (`MachineWireGlobalTile`) works on any `IElectricConsumer`, so a pole could be switched off by a vanilla wire. Left as is; it is a test item, and arguably a nice feature.

The setter is `protected`, so this fits in the subclass |

## 3. Multiplayer design (rule 9)

**Authority.** The server owns the link graph. Clients never create or remove links directly.

| Thing | Who | How |
|---|---|---|
| Link graph (`PoleLinkSystem`) | Server and single-player | Saved in world data. Clients hold a replica |
| Create / cut request | Owner client asks | `PoleLinkRequest` (to server) |
| Validation | Server | Sender alive; both tiles are poles; different poles; both free points exist; span within the wire's max; (no reach check since P7c); the player holds enough wire |
| Wire consumption and refunds | Server decides, owning client takes | The server only checks that its mirror of the sender's inventory (cursor slot 58, then 0-57) holds the cost; the owning client takes the items when the `PoleLinkChanged` answer arrives (cursor first, then selected item, then the rest) and syncs each changed slot with `SyncEquipment` (slot 58 is the cursor), the same split as `BucketPour` and `CartInputNet`. Refunds are spawned by the server with `Item.NewItem`, once |
| Replica update | Server broadcasts | `PoleLinkChanged` carries the **complete slot list of each affected pole**, so a repeated or out-of-order packet cannot drift (same idea as `WireChanged`) |
| Join | Server | `JoinSync` provider `"pole-links"` sends every link |
| Power grid | Server (and single-player) | `gridNeedsRebuilding = true` on every link change. Clients receive `isOn` through the machine snapshot as today |
| Pending link, preview, hit-testing, hanging-wire drawing, later the rope simulation | Client only | Never saved, never sent |

**Single-player** runs the server handler directly (rule 10): `PoleLinkNet.RequestLink` and `RequestCut` call the handler when `netMode == SinglePlayer`.

**Rejected requests.** The server answers the sender alone with the current state of the two poles, so the client never stays out of sync. No client prediction: the link appears when the server confirms, which is one round trip.

**Entity vs link lifetime.** Links are keyed by the pole entity's top-left `Point16`, not by entity ID, so they survive the entity bootstrap scan (patch 4.5) and entity re-sharing. The flood fill skips a link whose pole entity does not exist yet. Links are removed only when a pole is **killed** (event-driven), never by a scan at world load, so a pole that has not been bootstrapped yet cannot lose its links.

## 4. Data model

```
PoleLink
  Point16 A, B          // entity top-left of each pole
  byte SlotA, SlotB     // connection point index on each pole
  CustomWireType Wire   // Copper, Tin or Gold
  ushort Cost           // wire items paid (refund amount)

PoleLinkSystem : ModSystem   (Common/Systems/PoleLinkSystem.cs)
  List<PoleLink> Links
  Dictionary<Point16, PoleLink[]> BySlot   // per pole, length = LinkPointCount
  public float CopperSpan, TinSpan, GoldSpan, WireTilesPerItem   // tunables, instance fields
  TryAdd / Remove / RemoveAllFor(Point16 pole) / GetLinkedPoles(Point16)
  SaveWorldData / LoadWorldData   // parallel lists, like CustomWireSystem
```

`PowerPoleTileEntityBase : ElectricConsumerMachine` (folder `Content/Tiles/Machines/ElectricalConsumers/PowerPoles/`) adds `abstract PoleBoard[] Boards`. Each `PoleBoard` holds its PNG path, size, attach point and link points (pixels inside the board PNG). `LinkPointCount` counts the points of all boards (platinum order: upper board's two points, then the lower board's). Connection point world position = `Position * 16 + board.AttachOffset + (point - board.Pivot)` (`GetLinkPointWorld`).

**Connection point coordinates come from the art.** Give the pixel position of each crossarm tip inside its crossboard PNG (x, y from that PNG's top-left) and each PNG's size. The pivot is the PNG's centre, so nothing else needs converting.

**Point choice (decided; the CLIENT side was CHANGED in P6c: hovering a pole selects the connection point closest to the MOUSE, free or not, only that point is highlighted, and it is the start and the end of the link; a taken point is invalid and a click on it does nothing, nothing is chosen for the player. The server rules below are unchanged and still apply to requests without hints, such as `/plink`).** Original text, now historical: The player never picks a point from a list. The client starts the pending wire at the free point closest to the player and, when the cursor is over a second pole, ends it at that pole's free point closest to the start point; both slots travel in the request (`hintSlotA`, `hintSlotB`) so the preview and the final wire match. The server uses a hint when that point exists and is free, otherwise it refuses with `SlotTaken`. A request without hints (slot 255, what the temporary `/plink` sends) lets the server choose: for A the free point closest to B's footprint top, for B the free point closest to A's chosen point. A pole with no free point refuses the link; the preview still attaches to the closest point but is drawn red and cannot be committed.

### P6. Player input: pending link, preview, request

While pending, the wire follows the cursor as a hologram even when the player walks away. The first pole can be far away by then, which is fine because the request carries both pole tiles and the server verifies both are poles, not that the player is near the first.

### P9. Living wire (started 2026-10-26, right after P7c; P8 was skipped)
LUMINANCE API FINDINGS (read from the Luminance source, github.com/LucilleKarma/Luminance, commit b2468df of 2026-08-21; the DLL in ..\ModAssemblies may differ slightly, so check `Luminance.xml` beside it before relying on a signature): (1) `PrimitiveRenderer.RenderTrail(IEnumerable<Vector2> positions, PrimitiveSettings settings, int? pointsToCreate = null)` takes WORLD positions (it subtracts `Main.screenPosition` itself), needs more than 2 and fewer than `MaxTrailPositions` points, and needs at least 4 for smoothing; `PrimitiveSettings(WidthFunction, ColorFunction, OffsetFunction = null, Smoothen = true, Pixelate = false, Shader = null, ...)` with width and colour as functions of the 0..1 position along the trail. With `Shader = null` it uses Luminance's own `Luminance.StandardPrimitiveShader`, so NO custom shader is needed. (2) `Pixelate = true` is only legal inside `IPixelatedPrimitiveRenderer.RenderPixelatedPrimitives` (NPC or projectile) or an action queued with `PrimitivePixelationSystem.RenderToPrimsNextFrame(action, layer)`; anything else throws. The pixelated layers (`BeforeNPCs`, `AfterNPCs`, `BeforeProjectiles`, `AfterProjectiles`) are rendered to half-size targets drawn at 2x scale (so 2x2 px chunks), and they are composited around `DoDraw_DrawNPCsOverTiles` and `DrawProjectiles`. (3) In tModLoader's `Main.DoDraw` (1.4.4 branch patch read, check against 2026.08.3.0) `SystemLoader.PostDrawTiles()` runs BEFORE the NPC and projectile passes, so a Luminance pixelated wire would be drawn OVER the crossboards (which are drawn in PostDrawTiles), which reverses the P6a decision (wires behind the boards); a queued `RenderToPrimsNextFrame` action also lags one frame. A NON-pixelated `RenderTrail` called from PostDrawTiles keeps the draw order but is smooth, not chunky. The decision between these options is Ismail's (see the P9 chat).
Client-only visual upgrade, no netcode.
- DECISION (Ismail, 2026-10-27): option 3, our own pixel-snapped curve with `SpriteBatch` and `TextureAssets.MagicPixel`, drawn from `PostDrawTiles` behind the crossboards. No Luminance dependency, custom shader, extra render layer or one-frame lag. The Luminance findings above remain historical research, not the implementation.
- A small Verlet rope per visible link: node count from span, slack and sag from span, wind from `Main.windSpeedCurrent`, local player and NPC velocity pushing nearby nodes, damping, a node cap and a hard node-offset cap for performance and conservative culling.
- The connection point positions stay authoritative from the link data. Only the curve between them is simulated, and each client simulates its own. The pending-link hologram uses the same pixel renderer with a static rest curve.
- Span checks, the cut hit-test and the server KEEP USING THE RESTING POINTS (decided in the P9 handoff); this supersedes the earlier idea of cutting against the curve. Only drawing uses the swayed, simulated curve.
- Simulation culling (noted by Ismail 2026-10-26, a hard requirement for P9): the rope simulation (wind, player and NPC disturbance) must NOT run for a link that is off screen: no stepping and no allocation for it. When it comes back on screen its nodes restart from the rest curve (or resume), so it does not pop. Use ONE shared visibility helper for drawing and simulation so both cull identically. See also the Progress line "Known issues, not scheduled".
